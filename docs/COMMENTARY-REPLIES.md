# Replying to AI commentary — schema and storage

Design sketch. No UI here, and nothing implemented yet. The point is to settle
where a conversation lives before any of it gets built, because that decision is
what makes it one call per question instead of one call per page view.

## The idea

Commentary is one-directional today: the model remarks, you move on. This makes
each remark the head of a short thread you can reply to — "why do you say that?",
"what should I do about the afternoons?" — with the answer kept.

## Where commentary lives today

Four surfaces generate it, and they persist it four different ways. This is the
main thing the design has to absorb.

| Surface | Generated by | Persisted where | Survives a reload? |
|---|---|---|---|
| Entry | `/api/commentary` | `time_entries.commentary` (012) | yes, in the row |
| Day | `/api/day-commentary` | `day_reviews.commentary` (025), **only once the day is finalized** | live days: localStorage only |
| Session | `/api/period-commentary` | nowhere | no |
| Week | `/api/weekly-review` | nowhere | localStorage only |

Only the entry commentary has a stable, server-side home. So the thread table
cannot hang off "the commentary row" — for two of the four surfaces there isn't
one. It has to key off *what the commentary is about*.

## Schema

One table. Each row is a message; a thread is every row sharing a subject,
ordered by `seq`.

```sql
-- supabase/migrations/20261102_commentary_replies.sql
--
-- Replies to AI commentary. One row per message; a thread is every row with
-- the same (user_id, subject_type, subject_key), ordered by seq.
--
-- Keyed by subject rather than by a commentary row: session and weekly
-- commentary are not stored anywhere, and day commentary only lands in
-- day_reviews once the day is finalized.

CREATE TABLE commentary_replies (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id TEXT NOT NULL,

  -- What the thread is about
  subject_type TEXT NOT NULL CHECK (subject_type IN ('entry', 'day', 'session', 'week')),
  -- entry   -> time_entries.id
  -- day     -> 'YYYY-MM-DD'
  -- session -> 'YYYY-MM-DD:morning' | ':afternoon' | ':evening'
  -- week    -> week start 'YYYY-MM-DD'
  subject_key TEXT NOT NULL,

  -- Position in the thread, 1-based. The opening commentary is NOT stored
  -- here; it already exists on its own surface and is passed as context.
  seq INT NOT NULL CHECK (seq >= 1),

  role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
  content TEXT NOT NULL CHECK (length(content) BETWEEN 1 AND 2000),

  -- The commentary this thread hangs off, copied in at thread creation.
  -- Day and week commentary can be regenerated when the underlying data
  -- changes; without this snapshot an old answer would read as a non sequitur
  -- against new commentary.
  subject_commentary TEXT,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (user_id, subject_type, subject_key, seq)
);

CREATE INDEX idx_commentary_replies_thread
  ON commentary_replies(user_id, subject_type, subject_key, seq);

CREATE INDEX idx_commentary_replies_user_created
  ON commentary_replies(user_id, created_at DESC);

-- RLS: deny-all, matching every other table here. The service role key
-- bypasses it and the API route is what enforces ownership.
ALTER TABLE commentary_replies ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Deny direct access - use server" ON commentary_replies
  FOR ALL USING (false);

COMMENT ON TABLE commentary_replies IS
  'Follow-up conversation on AI commentary. Threads are stored, never regenerated.';
COMMENT ON COLUMN commentary_replies.subject_commentary IS
  'Snapshot of the commentary the thread started from, so answers stay legible if it is later regenerated.';
```

### Watch the migration filename

Supabase applies migrations in lexicographic order. The last numeric file is
`033_`, but `20260201_add_productivity_target.sql` sorts after it — so a new
`034_` file would run **before** that one on a fresh database. Use a dated name
(`20261102_`), not `034_`. Worth fixing the mixed convention at some point; this
is not the migration to do it in.

### Why one table, not a `threads` + `messages` pair

A threads table would carry an id, the subject, and a created_at — all derivable
from the messages. It buys a join and an extra write per first message, and the
only thing it would uniquely hold, `subject_commentary`, sits fine on the rows.
If threads later need their own state (archived, pinned, a title), split then.

## API shape

One route, `/api/commentary/thread`:

- **`GET ?subject_type=day&subject_key=2026-11-02`** → the stored messages. Pure
  database read, no model call. This is what the UI opens with.
- **`POST`** `{ subject_type, subject_key, subject_commentary, message }` →
  appends the user message, generates one reply, appends it, returns both.

Both go through `getServerSession` and `RATE_LIMITS.ai` keyed by user id, like
every other AI route — that part is already consistent across the app.

### Context sent to the model

Assembled server-side, never trusted from the client beyond the message text:

1. The subject's own data, re-derived server-side (the day's summary, the entry,
   the week's stats) — the same shape the original commentary was built from.
2. `subject_commentary` — what the model said.
3. The thread so far, capped (see below).
4. The new question.

## Cost and the guard rails that matter

Rough per exchange on gpt-4o-mini: ~600 tokens in, ~120 out, so a fraction of a
cent. A thousand exchanges is small change. **Cost per call is not the risk.**

What actually burned calls in this codebase was never a feature — it was
regeneration and retries. Three rules, each one a bug we have already had:

1. **Threads are read, never regenerated.** A GET must never call the model. The
   day commentary bug was exactly this: a cache that died on reload, so every
   visit re-asked. Replies cannot be fingerprint-cached the way commentary is —
   the input is free-form — so persistence is the only mechanism available.
2. **One attempt per send, with an explicit guard.** The flicker bug was an
   effect gated on the state its own request set, retrying ~26 times a second
   whenever a request ended without a result. A send is user-initiated, which
   helps, but the reply-rendering effect must not be able to re-fire on failure.
3. **Cap the thread.** Suggested: 6 user messages per subject, `max_tokens` 200,
   and only the last 6 messages in context. Without a cap, context grows with
   every turn and cost grows quadratically. Return 409 at the cap rather than
   silently truncating, so the UI can say so.

Also: keep replies out of the summary prompts. If a thread fed back into the
day commentary, the fingerprint would change on every reply and the caching
built in `ai-text-cache` would regenerate the commentary each time — turning a
cheap feature into an expensive one.

## Build order

1. **Resolve the duplicate day review first.** `/day-review` and
   `/review?tab=day` are two live implementations of the same screen. Build this
   on one of them and it either has to be built twice or quietly only works in
   one place. Today's `Win` bug came from exactly that split.
2. Migration + `GET`/`POST` route + route tests. No UI. Verifiable with curl.
3. UI on the day review only.
4. Extend to entry, session and week once the shape has survived real use.

Starting with the day review is also the cheapest test of whether you want this
at all: it is the commentary you actually wanted to reply to.

## Open questions

- **Does the week subject need a snapshot at all?** The weekly summary is not
  persisted server-side; `subject_commentary` would be the only copy of it that
  ever reaches the database. That may be an argument for persisting the weekly
  coach summary properly, which would also let it survive a cleared browser.
- **Should a reply be able to change something** — add a plan item, adjust a
  target — or is it read-only reflection? Read-only is a much smaller surface
  and worth shipping first.
- **Retention.** Threads are small, but they are the only free-text the app
  stores. Worth deciding up front whether they are kept forever.
